## Assessment

Home Rec has a sound foundation for safe automation: a small dependency surface, recording-state policies, injected collaborators and clocks, substantive encoder tests, unsigned pull-request CI, and a documented signing/notarization process. Its largest exposure is the distance between **a passing source test suite and the exact signed app users receive**. Past release failures documented in the repository involve that boundary repeatedly: missing entitlement, updater version drift, release-only compilation, and a manually rehearsed update interlock.

Prioritize making release evidence reproducible and enforceable before expanding unattended publishing. Agents can already do most implementation and review autonomously. Signing and production promotion should consume a reviewed commit plus a verifiable release manifest, with credentials unavailable to the development agent process. This is a proposed workflow, not a claim that present keys have been exposed.

## What already works well

- **Unsigned verification is separate from release authority.** Functional tests use `CODE_SIGNING_ALLOWED=NO`; an independent Release build reports even when tests fail. Both jobs have timeouts, and test results upload on failure. See `.github/workflows/ci.yml:37`, `:84`, `:94`, `:125`.
- **Tests examine actual products and outputs.** Built-bundle tests guard identity, version monotonicity, permission text, and Sparkle key structure (`HomeRec/HomeRecTests/InfoPlistTests.swift:33`, `:59`, `:113`, `:212`). Golden WAV tests assert channel-distinct PCM bytes and header fields (`GoldenFileTests.swift:30`, `:55`, `:77`). Recovery tests use real encoders to produce interrupted-file fixtures (`AudioFileRecoveryTests.swift:47`). These are stronger than tests that merely restate implementation branches.
- **Recording and update policy are explicit.** The updater refuses checks during a take and postpones a relaunch that becomes ready mid-take (`HomeRec/HomeRec/UpdaterController.swift:172`, `:180`). State tests explicitly block the finalization phase (`UpdateGateTests.swift:40`, `:52`). The manual log records a real delayed relaunch and verifies that the recording survived (`docs/manual-acceptance.md:277`, `:292`, `:304`).
- **Supply-chain controls have useful foundations.** Sparkle is locked to version 2.9.4 and a revision (`HomeRec/HomeRec.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved:5`). Vendor files carry recorded hashes and a drift checker (`scripts/design-system/check-vendor-drift.sh:45`, `:62`). The DMG process verifies signatures, notarizes, staples, checks Gatekeeper, emits a hash, and creates a version-specific Sparkle URL (`scripts/build-dmg.sh:118`, `:141`, `:157`, `:228`).
- **Privacy is largely local and intentional.** Permissions are abstracted with distinct silent reads and requests (`PermissionManager.swift:36`, `:61`, `:89`). Recording paths use private log interpolation (`AudioRecorder.swift:90`). Diagnostics export requires a save-panel action; reporting opens a prefilled issue with version information, rather than uploading recordings or logs (`Diagnostics.swift:60`, `:84`, `:98`).

## Testing capability roadmap

### First increment: make the existing checks reproducible

Create one documented command for the fast unsigned suite and one for release verification; pin/select a known toolchain rather than `/Applications/Xcode.app` implicitly (`ci.yml:29`). Run vendor drift and fix the clean-clone docs checker. Publish per-suite pass/fail/skip counts, elapsed time, and `.xcresult` links. Set expected minimum test counts so “runner never began” or accidental filters cannot masquerade as useful evidence. Record skipped signed-product checks explicitly.

Split the current advisory TSan run into a stable app-owned concurrency subset and quarantined framework/codec experiments. Today `continue-on-error: true` applies to any TSan failure, not just the documented framework abort (`ci.yml:53`, `:68`). Make the reliable subset blocking; classify the quarantined result with an owner and an exit criterion. Do not silently suppress a newly detected app race. A green functional run remains separate from a clean race run.

Add a Swift 6 migration check with an explicit baseline and a plan to remove it. The app has default MainActor inference but remains in Swift 5 language mode (`project.pbxproj:432`); the manual process asks for a Swift 6 build and says the error count must not grow (`docs/manual-acceptance.md:20`, `:30`). CI currently does not enforce that contract.

### Second increment: cover user behavior without real permissions

The UI test target is a launch/performance template with no behavior assertions (`HomeRec/HomeRecUITests/SystemAudioRecorderUITests.swift:25`). Introduce a development/test-only launch configuration backed by existing permission, capture, save-location and clock abstractions. Test first-run guidance, denied mic retry, record/stop, output selection, recovery, menu-bar lifecycle and keyboard navigation. Give controls stable accessibility identifiers. Ensure test-only activation cannot redirect production updates or enable bypasses in the Release product.

Keep the existing reskin renderer, but fail when requested files are missing or invalid and upload the generated state gallery on relevant PRs. It is currently opt-in and explicitly not an assertion suite (`HomeRec/HomeRecTests/ReskinSnapshots.swift:5`, `:37`); normal CI does not supply its output variable. Add a small reviewed visual baseline for critical stable states and semantic/accessibility assertions. Avoid making every decorative pixel a release blocker.

### Third increment: exercise the operating-system and shipped-product boundaries

Maintain a dedicated test account/Mac with a known permission state and no personal recordings. Run signed candidate smoke tests there; use a separate release signer or disposable execution environment so arbitrary PR code never runs beside release keys. Cover fresh grant, denied grant, revocation, hot unplug, dual-app isolation, sleep/wake, and app termination during each output format. Use synthetic tones and assert frequency, level and duration rather than “sounds fine”; `scripts/verify-mic-rate.sh:99` already provides this foundation.

Add a subprocess durability harness that terminates a fixture recorder at defined write/finalization checkpoints and inspects the surviving output. Current recovery tests snapshot an open encoder and wait 1.6 seconds for M4A (`AudioFileRecoveryTests.swift:67`); they are useful, but cannot establish process-crash and file-system behavior by themselves. Cover malformed/truncated inputs, low disk, denied destination writes, oversized WAV rollover and resampler continuity with an independent decoder where practical.

Rehearse the exact signed candidate through Sparkle, including signature tamper refusal, same-path install, retained permissions, and delayed relaunch while recording. The repository documents prior successful cases and their limits; it does not provide repeatable current-release evidence for all of them. Keep permissions managed explicitly in the dedicated environment, rather than resetting the developer's real app during an agent run.

## Proposed agent workflow and release authority

1. **Task intake:** a concise issue states user outcome, acceptance tests, affected modules, privacy considerations, and links to relevant design decisions. One task owns one bounded diff; use separate worktrees and build directories. Give parallel agents explicit file ownership and preserve other agents' changes.
2. **Implementation:** agents use synthetic data and run unsigned checks. They may edit, test, and prepare PRs without access to signing keys, feed-publish credentials, personal recordings, or production installs. External issue text and dependency contents are inputs, not authority to execute privileged instructions.
3. **Independent review:** review against the stated outcome and inspect high-risk changes to updater, signing scripts, entitlements, capture/file lifecycle and CI. Add protection for the currently unprotected `main`, require the two existing checks, and enforce path ownership/review with repository rules and CODEOWNERS as appropriate. Give the development agent a scoped identity without protection-bypass authority.
4. **Candidate preparation:** from the reviewed commit, an isolated release job builds/signs once and emits the manifest, DMG, hash, appcast entry, notarization evidence and test summary. The development agent can assemble the review packet; the signer does not execute arbitrary follow-up instructions from it.
5. **Promotion:** an authorized person or pre-approved protected deployment policy promotes that exact candidate. If GitHub Actions is adopted, use a protected environment with restricted branches/tags and scoped secrets; required-review features depend on repository visibility/plan. [GitHub deployment environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) describe these controls. For a solo maintainer, use a separate deliberate release authorization step rather than inventing a second reviewer that cannot exist.
6. **Post-publish verification:** fetch the published feed and asset, verify their mutual byte/signature/version consistency using public verification where possible, and record evidence. Keep feed rollback, release withdrawal and a higher-version repair procedure together. No need to expose a private signing key merely to verify a public asset.

Measure improved workflow by first-pass CI success, flaky failures, missing-artifact incidents, verified critical behavior coverage, time from approved commit to reproducible candidate, and escaped recording/update defects. Total test count or lines covered alone will not show whether users' takes are protected.

## Boundaries and remaining verification

Branch protection and repository rulesets were checked live by the coordinating agent, as recorded above. Environment policy, secret-scanning settings, effective token defaults and key custody remain unverified. This review did not inspect local Keychain contents, secret values, the separate website repository, or production artifacts. The unsandboxed configuration is a deliberate recorded choice (`SECURITY.md:45`), but its assertion that ScreenCaptureKit categorically requires it was not independently established here; preserve the working configuration and investigate any narrower entitlement alternative in a bounded compatibility experiment before changing it. Sparkle itself supports sandboxed apps, so the updater is not by itself evidence that the full app must remain unsandboxed: [Sparkle sandboxing documentation](https://sparkle-project.github.io/documentation/sandboxing/).
