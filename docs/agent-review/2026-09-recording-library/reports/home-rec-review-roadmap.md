# Home Rec — product and roadmap review

Review date: 2026-09-05. Source reviewed: public checkout at `2f9c42d` in `home-rec/`. This is a read-only assessment; proposals below have not been implemented. Live GitHub facts were verified by the coordinating reviewer: no open issues or pull requests; latest published release `v1.1.1`, published 2026-08-22 at 12:04 UTC, resolves to `c877b37`; current HEAD `2f9c42d` is one later commit, fixing release-script generation of update-dialog notes, and its CI is green. Deployment of that change to the live feed was not verified. Private backlog and technical-debt documents are explicitly excluded from the public repository and were not available to this reviewer; their location was requested from the user.

## Recommendation

Make the next release about **confidence that the intended audio reaches a playable file**. The project already has enough useful features to validate its positioning. The strongest opportunity is to make recording, installation, permissions, recovery, and updates dependable across the distributed application, then improve the few interactions people repeat most often.

The intended product is unusually clear: a free, private, native recorder with one primary action, no routing setup, and audio kept on the Mac. Preserve that. A roadmap ordered by the amount of code already written would put monitoring next; a roadmap ordered by user consequence puts shipped microphone behavior, capture integrity, failure recovery, and release evidence first.

## Opportunities that fit the product

**Make “your recording is safe” observable.** A successful stop should clearly show the file that was finalized; a failed stop should never look like success. A brief “update will install after recording” explanation can remove the apparent dead-button behavior recorded in the update rehearsal. Consider a small interrupted-recording notice after launch, limited to the selected recording directory, with explicit recovery action. Do not auto-repair or search the whole Mac merely for discoverability.

**Learn without telemetry.** Use voluntary, structured issue reports and a small consented usability session: installed version, source/format, expected behavior, outcome, and optional reviewed diagnostics. Do not require uploaded recordings. Product decision measures can be first successful take without coaching, ability to find the saved file, reproducible failure reports, and incidents of lost/incorrect audio per release. Release engineering measures can be time to a trustworthy test result, escaped regressions, and percentage of changed user paths with artifact-linked acceptance evidence. These do not require adding background collection.

**Publish a small, truthful roadmap.** Keep internal prioritization private, but provide public Now / Next / Later items with user outcome, dependencies and status: proposed, experiment, implemented, packaged, verified, released. Remove completed work from “Next,” link to release evidence, and identify manual checks that are not yet run. Prefer this over publishing internal planning documents wholesale.

## Agent work design

Each issue should contain a concrete user trigger, current/desired behavior, invariant at risk, files or responsibilities owned by the agent, required evidence, and release implications. For a microphone fix, “tests pass” is inadequate: the task should explicitly require a packaged-app entitlement check and audible/nonzero decoded output after the real permission flow.

Assign parallel work by independent boundaries: product/acceptance specification, implementation, adversarial verification, and release preparation. One integrator owns the recording state machine and release manifest during a change; several agents should not independently broaden those shared surfaces. Reviewers should test the nearest false positive—for example, two apps playing for isolation, or a tampered but otherwise valid update for signature rejection.

Keep worktrees and build output isolated; record the base commit and final tested commit in each handoff. A commit, passing unit suite, unsigned Release build, signed DMG, and published update are distinct deliverables. Permission-sensitive GUI checks belong on a dedicated local test environment with a person handling system consent. Broadening agent authority to production signing secrets or modifying the user's real TCC settings does not solve a testing gap.

## Explicitly defer or avoid

- System-plus-microphone mixing, effects, routing graphs, transcript/cloud features, accounts, and telemetry: these would materially change the simple private recorder proposition. Reconsider only with an explicit product decision and demand evidence.
- A full preferences window solely because it appears on the old roadmap; add one when real settings no longer fit the compact surface.
- Major architecture replacement or Core Audio migration solely to appear modern. Evaluate against a concrete capture/permission problem and measured improvement.
- Wiring dormant monitoring into production to finish existing code before its hardware acceptance passes.
- More superficial tests that assert only timer duration, a mocked transition, or that an app launches; raise the quality of evidence around actual user outcomes.
- Treating a historical manual pass as coverage for a new binary, or treating an unchecked template box as proof a check has never passed. Record dated runs separately, as the repository already does.

## Limits

This review reads source, tests, recorded acceptance results, and live GitHub metadata verified by the coordinating reviewer. It does not claim current live application testing, real hardware capture validation, a complete audit of private plans, or fresh confirmation of third-party product comparisons. Tagged-source identity is established; packaged-app behavior and feed delivery require the separate artifact verification described above. The architecture and security reports provide deeper implementation and deployment findings; this report orders product work around their consequences.
